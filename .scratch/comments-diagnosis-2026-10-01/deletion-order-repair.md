# 删除顺序导致主评论占位残留

Status: resolved (local implementation and runtime)
Date: 2026-10-01

用户报告：先删除主评论再删除回复，会在公开页面和后台留下“已删除”；先删回复再删
主评论则没有残留。此请求授权修复本地代码和运行库；未更新云端。

## 可重复证据与根因

原生 MySQL 上通过真实 DELETE HTTP 路由复现，使用独立数据库会话检查物理记录：

```powershell
# backend 目录
.\.venv\Scripts\python.exe -m pytest tests/test_comment_deletion_mysql.py -q
```

修复前：4 个场景中 3 个失败、1 个通过。先删主评论、穿插删主评论、最后删除隐藏
回复时均残留已删除主评论；先删全部回复再删主评论通过。

已删除主评论在仍有回复时保留占位是既有正确行为。缺陷在于删除回复只删除自身，
没有在最后一条回复消失后重新检查、清理已删除的主评论。新会话能读到残留数据库
记录，排除了单纯前端缓存解释；前端删除成功后已调用重新加载。

## 修复和边界

- 删除回复后先 flush，在既有讨论锁范围内检查原评论状态和剩余回复。
  只在原评论已删除且没有任何回复时删除原评论，随后一次提交。
- 隐藏回复仍属于存活回复，不能因公开不可见就连带删除。仍公开/隐藏的主评论
  不会因其最后一条回复删除而被删除。
- `0019_prune_deleted_roots` 数据迁移清理历史占位，仅匹配已删除、正文为空、
  没有回复的顶层评论；MySQL 多表 DELETE 避免同表子查询限制。
  降级不恢复已经删除的占位，也不编造正文。
- 本地运行库已从 0018 显式升级到 0019，清理 1 条符合条件的历史残留（ID 1）。
  其余 1 条评论的所有字段保持一致，迁移前后 SHA256 均为
  `cf641ce0951e85420757fc26687f6ca7db04c3193a0971633c16f941bf58d386`。
  空的已删除主评论数量变为 0。
