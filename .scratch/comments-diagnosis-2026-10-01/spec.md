# 评论体验修复方案

Date: 2026-10-01
Status: implemented; local acceptance verified; cloud deployment pending
Related: [云端诊断与重放证据](./diagnosis.md)
Execution boundary: 用户于 2026-10-01 授权按 spec 完成本地代码及验证；云端部署不在本次范围。

## 已由用户确定的行为

1. 评论 Markdown 的受支持语法在公开正文、预览、后台正文中正确排版。
2. 评论列表成功加载时，将当前页取得的评论标为已读；其他页的新评论仍提示。
3. 后台继续按最新评论排序。回复卡片标明“回复原评论 · @作者”，并展示原评论摘要。
4. “查看完整讨论”打开后台侧栏，展示原评论及全部一层回复。
5. 保持现有一层回复。即使从某条回复处操作，发布对象仍是原评论，界面明确说明。

## Markdown 排版

新增局部共享排版样式，应用到公开评论正文、公开 Markdown 预览和后台评论正文；
侧栏评论正文复用相同规则。覆盖服务端实际支持的 h1–h6、p、strong/em、ul/ol/li、
blockquote、行内 code、pre/code、链接、hr/br。标题有字号/字重层级，列表恢复
序号或项目符号，代码块横向溢出时只在块内滚动，手机页面不被长代码撑宽。

保留服务端 sanitization、安全链接限制与禁止图片/媒体的规则。不要把这项修复
扩成文章编辑器或新增表格、数学、语法高亮等能力。当前服务端 commonmark 渲染器
没有承诺支持所有 Markdown 扩展，验收以受支持语法为准。

## 已读与未读

现有全局 last_seen_at 时间水位不适合“当前页已读”：它既受到历史时间混用影响，
也会隐式抹掉其他页的提醒。建议改为持久化的逐评论已读标记，例如 nullable
admin_read_at；继续沿用当前后台共享的已读状态，暂不引入每管理员独立收件箱。

- 评论列表读取本身不更新已读，避免响应失败或前端未成功加载时误清除。
- 前端成功接收并显示当前页后，以返回的评论 ID 集合调用受管理员鉴权及 CSRF
  保护的幂等确认已读接口。重复请求不产生副作用。
- 服务端仅更新请求集合内存在且可计入未读的读者评论；博主回复不产生未读数。
- 现有未读过滤规则继续适用：仅公开的读者评论/回复计数，隐藏/已删除内容不计数。
- 确认接口返回当前准确未读总数；导航和页面使用同一状态。进入评论页面不能
  无条件把提示数清零，后台旧请求也不能覆盖后返回的新状态。
- 新留言即使在“读列表”和“确认已读”之间到达，只要不在已读 ID 集合内，就继续
  保持未读。翻页仅确认新加载页面。侧栏成功展示的原评论及回复也属于已查看集合。
- 确认失败不假装持久化成功；保留提醒并允许重试，避免刷新后重新出现却没有解释。

历史迁移建议保守处理：保留旧状态数据以便核对，新逐条标记初始为空；历史公开
读者评论最多需要重新读一遍。不要依靠不可信的旧时间水位批量推断已读，也不要
通过加减 8 小时批量修改评论时间。新写入时间需统一 UTC；已有显示时间偏差作为
单独的数据核对项记录，除非有证据，不自动改历史值。

## 回复卡片与后台讨论侧栏

回复保留独立卡片与原有排序，增加显眼的“回复原评论 · @原作者”标签、纯文本摘要
和“查看完整讨论”。原评论卡片可显示其回复数与同一入口。摘要折叠为两到三行，
不能将未清洗的 Markdown 直接注入 HTML。

后台列表接口补充原评论上下文，并根据 parent_id 批量查询，确保父评论在另一页
仍可展示；避免每条回复单独请求。原评论已删除时显示“原评论已删除”，不编造
正文；已隐藏时后台展示内容并明确标注隐藏状态，继续遵守公开页的隐藏规则。

侧栏以 Root Comment 为入口，按时间先后展示原评论和全部 Comment Reply，
保留博主标记、隐藏/删除状态和现有管理动作。内容独立于列表分页；侧栏内一条
回复的操作必须说明“回复原评论 @作者”，并把原评论作为真正提交对象。

侧栏有明确标题和关闭按钮，支持 Escape、焦点进入/恢复；桌面从右侧打开，手机
可占满可用屏幕。长讨论在侧栏内部滚动。加载失败展示可重试状态，不清空原列表。
后台使用管理员接口取上下文，避免依赖公开页可见性；文章取消发布后也可继续管理。

## 验收条件

| 场景 | 期望 |
| --- | --- |
| 同一 Markdown 样例在公开正文、预览、后台、侧栏 | 标题有层级，列表有符号，引用与代码可辨识 |
| 恶意链接、原始 HTML、图片 | 按现有策略拒绝/转义，不新增注入通道 |
| 21 条未读，第一页成功取得 20 条 | 只确认这 20 条，提醒仍为 1 |
| 第二页成功加载剩余 1 条 | 提醒为 0；离开、刷新、重新登录仍为 0 |
| 旧评论 created_at 晚于当前 UTC | 查看并确认后仍可清除，不依赖时间比较 |
| 列表加载失败或已读确认失败 | 不误清未读，提供重试 |
| 加载后确认前新留言到达 | 新 ID 不被确认，保持未读 |
| 博主发布回复 | 不产生新的读者留言提醒 |
| 回复与原评论不在同一页 | 仍显示原作者、摘要及讨论入口 |
| 原评论隐藏或删除 | 后台清楚标注状态，删除正文不泄露/不虚构 |
| 点击回复卡片的完整讨论 | 后台侧栏显示正确原评论与全部回复 |
| 从回复条目发布回复 | 显示并提交到原评论，继续只有一层 |
| 手机宽度与长代码/长回复 | 页面无横向溢出，侧栏可关闭和操作 |

后续验证需区分 fixture 自动化与真实云端/MySQL：前端 fixture 覆盖布局、分页及
竞态；MySQL 集成覆盖已读持久化、幂等与并发；云端最终验证记录真实计数、页面
刷新与回复关系。此次诊断没有 GitHub 实际登录、后台交互修复或部署验收。

## 变更范围

- 后端评论模型/迁移、schema、服务与管理员路由：逐评论已读及原评论上下文/讨论读取。
- 前端 comments 类型/API client、评论管理页、AdminShell：准确未读状态、回复卡片及侧栏。
- 公开 CommentSection 和局部共用样式：Markdown 视觉层级及预览一致性。
- 回归覆盖：真实 MySQL 已读持久化，以及桌面/手机评论渲染、分页和上下文。

不修改评论身份认证、GitHub OAuth、公开一层回复规则或无关管理页面。
## 实现与验证记录

- `0018_comment_read_receipts` 新增 nullable admin_read_at 和未读查询索引，保留旧表及历史时间；
  未按 last_seen_at 推断任何历史已读值。
- GET 列表不再写已读；POST `/admin/comments/read` 接收最多 100 个明确 ID，受管理员和
  CSRF 保护，幂等保存后返回总数。大讨论分批确认，前端共享队列串行处理计数请求与确认。
- GET `/admin/comments/{id}/discussion` 可从根或回复找到完整后台讨论；列表批量提供父作者、
  纯文本摘要和状态。界面提取共用评论卡片，侧栏沿用 Reka 焦点管理，显式恢复开启按钮焦点。
- 新读者评论/博主回复显式写 UTC；响应日期携带 UTC 时区。历史时间未改，旧异常记录的实际
  发生时刻仍需核对，历史显示可能偏移；这是保留源数据而非推测批量纠正的结果。
- 本地真实 MySQL：14 项通过，覆盖迁移 head、分页确认、幂等、跨会话持久化、时间偏差、
  并发新留言、隐藏/删除/博主过滤、未发布讨论、一层回复、身份权限和 CSRF。
- 前端单元：20 个文件、146 项通过，其中 3 项验证旧计数竞态、失败恢复与分批 ID 集合。
- Playwright：桌面 Chromium 和 Pixel 7，16 项通过，使用隔离的 3103/8787 fixture 服务；
  覆盖分页、并发、导航刷新、失败重试、原评论跨页、侧栏焦点、正文/预览样式及移动端溢出。
- 增补列表失败的“重新加载评论”入口后，单独重验桌面和手机的列表失败恢复流程。
- 侧栏头部与关闭按钮固定在滚动内容之外，另行通过桌面和手机长讨论滚动、关闭和焦点恢复
  两项补验。整体 16 项及上述 4 项补验均通过。
- TypeScript、ESLint、Ruff、后端相关模块 mypy 及 Nuxt 生产构建已通过；构建产物包含
  最终的列表重试入口、侧栏内部滚动规则和评论动作图标排版。
- 测试运行可见 Nuxt 已有 NUXT_E4011/nostics 开发警告；目标侧栏流程无 pageerror/框架遮罩。
  全量 Vitest 退出码 0，但打印 happy-dom 帧销毁后的异步任务诊断；未修改无关测试运行时。
